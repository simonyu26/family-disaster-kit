## 議程

### 一、四項燈號檢查

每項只報燈號（綠／黃／紅）加一句話，黃燈、紅燈才展開。

| 檢查 | 報告串 | 綠燈的標準 |
|---|---|---|
| 進度表與 CHANGELOG 對齊 | 文書串 | 進度表、決策紀錄、CHANGELOG 的上線狀態一致（WP-04） |
| 策略目標沒偏移 | 災防顧問 | 對照 `docs/strategy-goals.md` 三條界線與反指標，沒有越線 |
| 發版、線上核對與用量 | 工程顧問 | 合併後都做了 E-11 核對（依 GitHub 合併與 Pages 部署紀錄、reviews/ 審查檔）；依 Simon 的「總覽」截圖，GAS 與外部查詢沒有接近免費帳號上限。不為此在後端加計數程式 |
| 安全與待辦都處理 | 文書串 | P0、P1 工項沒有卡住超過兩週；示警、緊急模式的審查都有結論（D-04） |

### 二、追蹤事項

上次行動清單的每一項：負責串、狀態。真的完成（已上線並核對）才結案，否則帶到下次。第一次開會沒有前次，改為列出目前所有進行中的 PR。

### 三、數據回顧

- **工程顧問**：這兩週合併與部署的 PR、E-11 核對結果、審查發現的問題，以及用量（依截圖）。期程是否落後：第一次會只報開發順序走到哪；從第一次會起訂預定日期，第二次會才比對。
- **文書串**：進度表各區工項數變化、決策紀錄筆數、P0／P1 剩幾項。
- **災防顧問**：對照策略目標的反指標：
  1. 開啟緊急模式到能按報案鍵的秒數有沒有變長；
  2. 遊戲化元素的比例有沒有變高；
  3. 防災、備災、救災相關功能與無關功能的數量比例，無關功能不可多於相關功能。

### 四、使用者回饋

Simon 與家人實際使用時回報的問題、App 內的回饋。使用者顧問整理成清單，標出影響緊急模式或應變流程的項目。

### 五、經驗與改進

- 每串報一個做得好的地方、一個下次要改的地方。
- 檢討哪些流程規則要改（例如這兩週的 W-26 通知規則），要改的列成選擇卡。
- 有沒有值得寫回協作 skill 的經驗。

### 六、下兩週方向

- 災防顧問、使用者顧問提重點：哪些安全或易用性問題最該先處理。
- 執行長、副執行長依開發順序（`reviews/dev-order-proposal.md`）提預定日期；工程顧問檢查相依與衝突（W-20、E-12），不自己排期程，維持審查獨立。
- 新功能凍結中（P-06），③ 待發展概念只討論、不排期，除非 P0、P1 已清完。

### 七、行動清單

每項寫明負責串和期程，由文書串寫進進度表（W-20）與決策紀錄（W-18）。

### 八、要 Simon 決定的事

整理成選擇卡，一張卡一題，附建議（W-13）。
